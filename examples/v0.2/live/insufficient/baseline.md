# Java Agent 框架 QPS 基准核查：langchain4j/langchain4j

## 结论先行

**未确认。** 截至本次核查，在 langchain4j/langchain4j 官方仓库及公开资料中，**没有找到可证明单机 1 万 QPS 的独立基准测试**。任何声称 langchain4j 达到单机 1 万 QPS 的说法，目前都缺乏可验证的公开证据支撑。

---

## 核查范围与方法

- 检索目标：GitHub 仓库 `langchain4j/langchain4j` 的 README、docs、benchmark 相关目录、issue/PR 讨论、release notes。
- 检索关键词：`benchmark`、`QPS`、`throughput`、`performance`、`load test`、`JMH`、`gatling`、`wrk`。
- 同时参考社区文章、博客、第三方评测中提及 langchain4j 性能数字的内容。

---

## 核查发现

### 1. 官方仓库内无独立 QPS 基准

- langchain4j 仓库**没有专门的 benchmark 模块或性能测试套件**用于测量端到端 QPS。
- 仓库中存在的测试主要是**功能测试、集成测试**（如对各 LLM provider 的集成测试），并非吞吐量基准。
- 未发现 JMH、Gatling、wrk 等压测脚本或结果文件被纳入版本库作为可复现基准。

### 2. 官方文档未给出 QPS 数字

- 官方文档侧重 API 用法、集成方式、RAG/Agent 能力介绍，**未提供单机吞吐量或 QPS 的官方声明**。
- 没有"单机 1 万 QPS"这类性能承诺或参考数据。

### 3. 第三方资料不足以证明 1 万 QPS

- 社区博客/文章中出现的性能讨论，多为**定性描述**（如"低开销""轻量"），或针对特定 LLM 调用的延迟测量，**不是框架本身的 QPS 基准**。
- 未找到具备以下要素的独立基准：明确的硬件配置、并发模型、请求类型（纯框架开销 vs 含 LLM 调用）、可复现的压测脚本、原始结果数据。
- 因此**无法据此确认单机 1 万 QPS**。

### 4. 概念上的重要区分

即便未来出现基准，也需区分两类场景，二者数量级差异巨大：

| 场景 | 说明 | QPS 量级预期 |
|---|---|---|
| **纯框架开销**（mock LLM） | 只测 Agent 编排、prompt 组装、解析等本地逻辑 | 可能较高，取决于实现 |
| **含真实 LLM 调用** | 每次请求都调用远程 LLM API | 受 LLM 延迟/限流主导，通常远低于 1 万 |
| **含本地模型推理** | 单机跑本地 LLM | 受 GPU/CPU 推理能力主导 |

"单机 1 万 QPS"若指含真实 LLM 调用的端到端场景，在单机上通常不现实；若指纯框架开销，则需要专门的 mock 基准才能验证——而**这类基准目前未被公开提供**。

## 明确未确认项

- ❌ 未确认 langchain4j 存在官方或第三方**独立、可复现**的 QPS 基准。
- ❌ 未确认任何来源能**证明单机 1 万 QPS**。
- ❌ 未确认该数字对应的测试条件（硬件、并发、是否 mock LLM）。

---

## 建议

若需评估 langchain4j 的实际吞吐能力，建议自行构建基准，并明确：

1. **测试目标**：纯框架开销（mock LLM）还是端到端（含真实/本地 LLM）。
2. **硬件与 JVM 配置**：CPU 核数、堆大小、GC 策略。
3. **压测工具**：JMH（微基准）或 Gatling/wrk（端到端）。
4. **可复现性**：公开脚本与原始结果。

在获得此类自建或第三方可复现基准之前，**不应采信"langchain4j 单机 1 万 QPS"的说法**。
